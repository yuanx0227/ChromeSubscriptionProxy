# 0.3.5 检测机制修复与冷启动实测

后续修复：0.3.6 增加异常期间每 30 秒自动复查，网络恢复后自动清除异常。当前恢复行为见 [0.3.6 网络恢复修复](NETWORK-RECOVERY-0.3.6.md)；下文保留 0.3.5 的历史检测与实测记录。

用户反馈重启 Chrome 仍显示“正在检查代理”，并且首个延迟结果约 1,400 ms，随后只有约 170 ms。本轮先用旧版真实 Chrome 和既有 HTTPS 入口复现，再修改检测机制。只读读取服务器已有订阅作为验收输入，没有改动服务器配置或用户身份。

## 已确认问题

0.3.4 对一次 fetch 从开始到返回的总耗时直接计时。重启后第一次包含代理认证、连接及 TLS 等初始化开销，与复用连接的后续结果不具可比性。同时，fatal 事件尚未复核就写入黄色“正在检查代理”提示、显示感叹号，并等待最短 30 秒的 alarm，导致可用线路也像发生了故障。

旧版从全新 Chrome 进程首次请求开始，四次点击结果依次为 **1379、172、173、172 ms**。这是实际代理请求，不是模拟时间；当次记录窗口没有捕获新的 Chrome 原始代理错误事件，所以没有把底层启动错误的具体成因说成已经复现。

## 现在的行为

- 手动测速：一次不计入结果的预热，然后三个顺序 HTTP 请求，显示其**中位数**。每次使用唯一查询参数和 no-store，仍走 PAC 保留的代理检测地址。
- 返回数值是预热后的 HTTP 请求往返时间，包含应用和服务端响应开销，不是 ICMP ping，也不保证恰好等于某个固定值。
- 代理错误事件仅触发静默复核，不清空已有结果、不显示“正在检查代理”、不先亮警告徽标。
- worker 活跃时约一秒后复核；Chrome alarm 作为 worker 被挂起时的后备。第一次访问失败，间隔一秒再试，连续两次都失败才提示检测地址未响应。
- 检测地址故障只能说明该地址的检查失败，不将其描述为所有网站或整条代理都不可用。
- 检测状态和结果保存到 storage.session，Chrome 重启后不继承旧错误/延迟。worker 在同一浏览器会话内唤醒仍可恢复当前检测状态。
- 网络检测脱离配置操作队列；测量时仍可选线、断开或改规则，变更会取消旧检测，防止旧结果覆盖新连接。自动检测自身的事件不再触发循环。
- 主界面不增加说明；结果的悬停提示说明“预热后 3 次代理 HTTP 请求的中位数”。

## 修复后的真实验证

同一台 Windows 的 Chrome 153、同一既有服务器 HTTPS 入口，使用隔离 profile 两次完整退出并重启 Chrome。真实订阅与代理请求未模拟，结束后清理该测试 profile 的扩展存储与代理设置。

| 冷启动 | 首次预热（排除） | 首次三个样本 | 首次显示 | 随后再次显示 | 启动警告 |
|---|---:|---|---:|---:|---|
| 第一次 | 1383 ms | 173 / 173 / 173 ms | 173 ms | 172 ms | 无 |
| 第二次 | 1422 ms | 177 / 178 / 177 ms | 177 ms | 177 ms | 无 |

额外的必要定向检查通过：预热排除、中位数抵抗单个高值、静默复核、一次失败后恢复、连续两次失败才警告、检测自身无循环、旧跨浏览器状态清理、检测过程中断开且结果不回写。Playwright 验证断开按钮在测速时仍可用。构建及 CRX 打包完成，版本 0.3.5。

入口：`checks/proxy-warning.mjs`、`checks/probe-ui.mjs`。真实对比脚本 `probe-baseline-live.mjs` / `probe-fixed-live.mjs` 通过 stdin 接收授权订阅，不把凭据写入源码；脱敏结果保存在 work 下。

用户更新时只需在 chrome://extensions 对目录版晴空点重新加载，确认 0.3.5，再重开弹窗。两次隔离冷启动的结果证明本次机制在所测环境中符合预期，不等于覆盖所有浏览器扩展冲突或网络状态。
