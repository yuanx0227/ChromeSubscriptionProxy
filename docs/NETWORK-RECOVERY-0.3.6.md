# 0.3.6 断网后的自动恢复

日期：2026-10-02。

## 问题与原因

0.3.5 收到代理错误事件后静默检查检测地址；连续两次失败会显示提示和感叹号。但是，开始检测时就清除了 `proxy-recheck` 的一次性 alarm，失败后也没有安排下一次检查。因此，网络后来恢复并不会清除旧异常，只有新的代理事件或手动“测延迟”成功才可能更新状态。

## 修复行为

- 首次代理错误仍约一秒后静默复核，连续两次请求失败才提示检测地址未响应。
- 检测期间和异常期间保留每 30 秒运行的 Chrome alarm。持续失败继续重试，检测成功后清除异常提示、恢复 ON 徽标并取消 alarm。Chrome 调度和设备休眠可能推迟执行。
- 手动检测失败也进入自动恢复；自动检测成功会清除旧的“检测失败”显示，不生成手动测速数值。
- 复查意图保存在 `storage.session`。后台被停止后重新唤醒时恢复 alarm；旧版会话中只保留异常但没有待检查标记的状态也会进入自动复查。
- 弹窗关闭不取消恢复。页面已经打开时，既有存储变更监听会刷新提示和按钮。
- 主动断开、换节点或改配置仍会取消旧检测和 alarm；代理控制冲突或当前配置不可用时停止复查。检测自身产生的代理事件不启动额外检测。

自动检测只访问保留的检测地址并经过当前节点，成功代表该次检测请求可达。

## 本次必要检查

仅运行 `npm run build`、`node checks/network-recovery.mjs` 和 CRX 打包。没有执行全量、回归、冒烟、哈希检查或服务器变更。

Playwright 在新建隔离 Chrome profile 中加载真实 MV3 产物，使用虚构订阅和模拟的失败/成功检测响应，验证了实际 Chrome 代理 API、30 秒 alarm、会话存储、后台生命周期和页面更新：

1. 手动检测失败后显示异常，创建 30 秒周期的 alarm。
2. 关闭弹窗后，真实 alarm 自动发起复查；两次模拟失败后保留恢复任务。
3. 通过 Chrome DevTools 的 ServiceWorker 命令确认后台进入 stopped 状态，再唤醒后台；确认旧 JS 全局变量已经丢失。
4. 恢复模拟响应成功，无需再次点击检测；下一次 alarm 自动清除提示及感叹号，停止 alarm，延迟保持未检测。
5. 检测请求尚未完成时主动断开，取消请求并清除 alarm，旧结果没有恢复 ON 状态。

脱敏结果：`work/network-recovery-result.json`。本次未操作用户日常 Chrome，未对真实网络或现有服务器执行断网/恢复验收。
